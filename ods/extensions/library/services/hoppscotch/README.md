# Hoppscotch Community

Local API development workspace for REST, GraphQL and realtime requests. Packages the MIT Community edition, its native admin setup and a dedicated PostgreSQL database. No Enterprise features or cloud account are implied.

## Setup and origin

Set `HOPPSCOTCH_DB_PASSWORD` to 64 random hexadecimal characters and `HOPPSCOTCH_ENCRYPTION_KEY` to 32 random hexadecimal characters. Startup checks both formats before running native Prisma migrations; a migration failure prevents application startup. Keep both secrets with backups. Changing the encryption key prevents recovery of encrypted application data; changing the password requires updating the existing database account, not merely its environment.

Open **http://localhost:11090/admin** to complete native onboarding, then **http://localhost:11090/** for the client. Use `localhost` consistently: URLs and allowed origins are configured for it. Changing `HOPPSCOTCH_PORT` updates these URLs together. Access through a different host or ODS proxy needs explicit origin/reverse-proxy configuration.

The owner must choose and configure authentication in native onboarding. Email login requires an actual configured SMTP transport; OAuth requires provider credentials. The first admin login establishes administrative access. No email is sent, account seeded, provider configured or onboarding token generated by this recipe. Initial setup is reachable from the host loopback and other ODS containers; complete it before granting other users access. Installation/readiness alone does not mean authenticated team synchronization is ready.

## Requests and project use

Browser requests are subject to target CORS rules. For localhost project APIs, configure the project's CORS for this origin or deliberately set up a supported interceptor. This recipe does not install a browser extension, trust a certificate, launch a desktop agent or silently relay API credentials through a third-party proxy. Review the selected interceptor before sending sensitive requests. No sample collection is executed and no Playground files are imported automatically.

Collections/environments can be imported and exported through the application. Browser-local data depends on the browser origin; authenticated shared data uses PostgreSQL. Neither is an automatic Portal project association. Native setup remains necessary while chat configuration orchestration is unfinished.

## Persistence and runtime

`hoppscotch-db-data` retains PostgreSQL data on an internal network without a host port. Back up using PostgreSQL tooling or a stopped consistent volume copy before upgrades. The application runs as UID 1000 with GID 0 and a writable image filesystem because upstream substitutes frontend configuration at startup. It has two CPUs and 2 GiB RAM; the database has its own bounds. No GPU/model settings change.

The subpath server uses internal port 8000 and exposes `/`, `/admin` and `/backend` through one loopback port. The healthcheck requests the database-backed onboarding status through that server, rather than checking only the static page. It does not validate login, WebSocket subscriptions or external APIs.

Official version 2026.8.1 and PostgreSQL images are digest-pinned for Linux containers. Application image supports amd64 and arm64; Windows/macOS require a Linux-container Docker runtime. Image build, migrations, onboarding/authentication, imports, API calls, WebSockets and restore/platform execution remain runtime-pending. No containers or model inference were started.
