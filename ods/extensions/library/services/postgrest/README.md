# PostgREST: workflow artifact records

PostgREST 16.3 exposes structured artifact records through native REST filters,
pagination and PostgreSQL transactions. A dedicated PostgreSQL 17.11 database
owns the data and authorization grants. This API stores **metadata and references**;
it does not copy artifact files, run jobs, or provide object storage.

## Enable

From `ods/` on Linux, prepare private database storage:

```bash
sudo install -d -m 0700 -o 70 -g 70 data/postgrest
```

In Extensions, provide distinct long random values for
`POSTGREST_POSTGRES_PASSWORD` (initial database administrator),
`POSTGREST_DB_PASSWORD` (initial API authenticator) and `POSTGREST_JWT_SECRET`
(at least 32 characters for the trusted HS256 issuer). Enable PostgREST.
`POSTGREST_PORT` changes the default host API port 3005; `BIND_ADDRESS` defaults
to loopback. Trusted ODS clients use `http://postgrest:3000`.

The initial schema contains `api.artifacts`:

| Field | Contract |
| --- | --- |
| `id` | UUID primary key; generated by PostgreSQL when omitted |
| `title` | Required text with 1–500 characters after trimming spaces |
| `metadata` | JSON object, defaults to `{}` |
| `created_at` | Timestamp with time zone, defaults to insertion time |

For example, a writer can POST `/artifacts` with
`{"title":"Local transcription","metadata":{"path":"transcripts/run-42.txt"}}`.
`Prefer: return=representation` returns the inserted record and ID. Readers can
GET `/artifacts?order=created_at.desc` or filter an ID with `/artifacts?id=eq.<uuid>`.
Use native ranges plus `Prefer: count=exact` when total counts are needed.
PATCH and DELETE use native filters; operators must supply intended filters to
avoid changing every visible row. A bulk insert is one database transaction:
one invalid row rejects the whole batch. Duplicate UUIDs return a conflict.

## Tokens and permissions

Issue a short-lived HS256 JWT using a trusted local issuer. Set audience
`ods-postgrest`, `role` to `ods_reader` or `ods_writer`, and an appropriate `exp`.
Send it as `Authorization: Bearer <token>`. Never give clients the signing secret:
anyone with that secret can issue writer tokens. Native validation rejects an
expired token or incorrect signature/audience; the issuer is responsible for
including an expiry. This recipe does not add an interactive login or token store.

- No anonymous database role is configured, so unauthenticated requests fail.
- `ods_reader` can SELECT artifact records. `ods_writer` can SELECT, INSERT,
  UPDATE and DELETE. Neither role can log into PostgreSQL directly or administer
  the database. All clients of a role share this workspace; there is no per-user
  row isolation or tenant identity claim.
- The API logs in as `authenticator`, which has NOINHERIT and no superuser,
  database/role creation, replication or RLS-bypass powers. It can assume only the
  two explicitly granted roles. It never receives the database administrator's
  password. Separate libpq environment fields preserve password punctuation
  without assembling a connection URI.
- OpenAPI follows visible relation privileges, but its method list is **not** a
  complete authorization receipt: it can advertise POST for a table visible to a
  reader. Actual PostgreSQL grants enforce denied operations.

The database joins a private internal network and publishes no ports. Only REST
port 3000 is published through the host mapping. Native admin port 3001 stays
inside ODS; it exposes readiness, metrics and schema-cache information to trusted
ODS peers. Dashboard health uses `/ready`, which checks the pool and schema cache.
The scratch API image has no shell/HTTP client and no synthetic Docker health
probe. `docker compose up --wait` by itself only establishes that API process
startup succeeded; verify native readiness and an authenticated request as well.

Both containers have read-only roots and dropped capabilities. API/database RAM
limits are 256/512 MiB. The pool is bounded to five connections, responses to
1,000 rows, and the two impersonated roles have five-second statement timeouts.
These are operational limits, not a request-size/disk quota or measured capacity.
Add separately reviewed TLS before remote/untrusted HTTP use.

## State and recovery

The SQL initializer runs only on an empty PostgreSQL directory. Existing data,
schema and grants survive recreation. Changing a seed password alone does not
change a stored role. Rotate `authenticator` with native `ALTER ROLE`, update
`POSTGREST_DB_PASSWORD`, then recreate the API so new connections use it. Keep the
database seed value current for future empty-directory recovery. Rotate the
administrator separately. Changing the JWT secret and recreating invalidates old
signed tokens for new requests; already running transactions may complete.

Back up the entire stopped `data/postgrest` directory with its credentials,
configuration and image pins, or use a separately qualified PostgreSQL backup
procedure. Restore into a separate directory owned by UID/GID 70 and the matching
version. Verify record contents, reader denials and writer mutations. Referenced
artifact files require their own backup. Disable retains database state. Upgrade
rollback uses the matching pre-upgrade copy; do not downgrade migrated files.

Schema extensions need explicit reviewed SQL grants. In-database PostgREST
configuration overrides are disabled, so database settings cannot silently replace
the recipe's exposed schema or JWT configuration. No arbitrary SQL RPC is seeded.

## Qualification

```bash
python -m pip install pytest 'psycopg[binary]==3.2.10'
python -m pytest ods/tests/test_postgrest.py -q
sudo --preserve-env=PATH env ODS_TEST_POSTGREST=1 python -m pytest ods/tests/test_postgrest.py -q -s
```

Linux amd64 native tests cover unauthenticated/invalid/expired/wrong-audience JWTs,
reader and privileged-role denials, Unicode CRUD, exact-count ranges, conflict and
atomic-batch rollback, metadata constraints, recreation, punctuation-safe native
database credential rotation, JWT rotation and complete cold data/grant restore.
A test-only client probes native `/ready`; it is not an extra product service.
Browser clients, external token issuers, TLS, load, database-outage recovery,
power-cut durability, ARM/native macOS/Windows and cross-version migration remain
unqualified.
