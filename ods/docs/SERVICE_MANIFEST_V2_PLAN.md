# Service Manifest v2 and deterministic planning

ODS accepts `ods.services.v1` and `ods.services.v2` manifests during the
migration window. V1 remains a compatibility format: only its explicit
`depends_on` edges participate in Assistant First planning. Capability-like v1
fields are intentionally non-authoritative.

V2 adds the complete declarative input needed for a read-only plan:

- stable service, release, data-schema, definition, and Compose identities;
- versioned capabilities, hard dependencies, optional capabilities, conflicts,
  and explicit provider priority;
- platform, architecture, container runtime, GPU, and driver requirements;
- integer download, disk, CPU, RAM, VRAM, and GPU estimates;
- host/container ports, networks, volumes, devices, exclusive resources, Linux
  capabilities, and host permissions;
- typed configuration metadata, including only secret key names and flags;
- digest-pinned images or reproducible build locks;
- readiness, health, hooks, timeout, rollback, persistent-data, backup,
  uninstall, purge, publisher, trust, and support contracts.

The canonical schema is `extensions/schema/service-manifest.v2.json`. The
library mirror is generated by `scripts/sync-manifest-schema.py`; both bytes
must match. Catalog generation computes newline-independent semantic SHA-256
digests for manifest and Compose definitions and includes only deterministic
planning material in `catalog_revision`.

## Planner boundary

`assistant_first_planner.py` is a pure function. It does not read files,
environment variables, clocks, networks, containers, or services. Its caller
must provide:

- the immutable catalog and catalog revision;
- a complete observed host-state snapshot and its canonical revision;
- the product-owned policy and its canonical revision;
- the requested services/capabilities, explicit provider preferences, missing
  configuration key names, and an explicit UTC expiry.

The planner recomputes state and policy revisions, resolves a stable dependency
DAG, checks compatibility, trust, permissions, ports, exclusive resources, and
hard capacity limits, and returns exact definitions, artifacts, operations,
resource deltas, configuration metadata, data/rollback effects, warnings, and
approval scope. Equal-priority providers are ambiguous unless the request names
one explicitly.

Canonical JSON is UTF-8, compact, key-sorted, contains no floating-point
values, and ends with one LF. The plan hash covers the plan body only; `planId`
is derived from that hash. Identical explicit inputs therefore produce
byte-identical output. A mismatched catalog, host-state, or policy revision
fails instead of silently replanning.

## API boundary

Authenticated clients first read `GET /api/extensions/planning-contract` for
the current catalog and policy revisions. `POST /api/extensions/plan` accepts a
strict, size-bounded JSON request and returns a non-cacheable plan. The policy
body is server-owned and cannot be supplied or broadened by the client.

The endpoint is dry-run only. It has no lifecycle, Docker, shell, download,
configuration-write, or service-control dependency. Phase 3 must re-observe
state immediately before execution and bind external owner approval to the
exact plan hash, revisions, actor, and expiry.

## Migration and validation

Bundled manifests may migrate in reviewed batches. A Docker v2 definition
without a digest-pinned image or reproducible build lock cannot produce a
successful plan. V1 definitions remain discoverable and carry exact definition
digests, but produce a visible legacy warning when selected.

Run:

```bash
python3 scripts/sync-manifest-schema.py --check
bash scripts/validate-manifest-schema.sh
bash tests/test-validate-manifest-schema.sh
pytest extensions/services/dashboard-api/tests/test_assistant_first_planner.py \
  extensions/services/dashboard-api/tests/test_extension_planning.py
```
